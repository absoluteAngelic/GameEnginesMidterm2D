# GameEnginesMidterm2D

I used the principle of inheritance to make the PlayerController script a singleton, by inheriting from a Singleton base class that contains the code that check if it exists already etc. This allows any script to become a singleton very very quickly, by changing the script inherited class from "MonoBehaviour", to "Singleton<ClassToMakeSingletonName>", we can instantly use ClassName.Instance to get its instance instead of adding the code to each class that should be a singleton. Inheritance was also going to be used for EnemySpawn and BubbleSpawn inheriting from the base Factory so that the specific Spawners could be used in the same places/inspector slots if necessary.

I used the principle of encapsulation by "hiding" the playerHealth variable behind a TakeHealth() method. This allows checks such as triggering the Lose() method if the player has no health left, every single time the player takes damage, so there's no chance of forgetting to check for death in various places that you could damage the player, and also takes less system resources than checking the player health in the Update() method every single frame. I would have used encapsulation with the UIManager singleton that I planned, so you could use UIManager.Instance.EnemyDied() to update the UI, instead of setting a variable.

I planned on using polymorphism in the factory by the generic factory Spawn method having different effects depending on the Spawner type. Unfortunately I ran out of time to implement this. The generic Factory class would be inherited from by EnemySpawn and BubbleSpawn. I had two spawn points on the player that would be chosen as the bubble spawn point depending on whether the player last moved left or right, and would give the bubble a set horizontal velocity in the correct direction. EnemySpawn would be used to spawn an enemy, and set variables so that they walk a set distance, then turn back and do the same thing. The distance and time to walk in one direction would be configurable. Both of these Spawners' Spawn methods would be called by the exact same generic factory method.

I used a singleton for the player class so that when enemies collide with the player, the enemy scripts can very easily take health away from the player without needing to find a reference to it, though the collision method could be in the Player script. I planned to use a singleton for the UI in a UIManager class, so that instead of having references to the individual UI elements, the enemy script Die() method could instantly add 1 to the "Enemies Killed" thing on the UI by just doing UIManager.Instance.EnemyDied(). This would also allow the player TakeDamage() method to instantly update the healthbar on the UI that I planned to have by doing UIManager.Instance.SetPlayerHealth(playerHealth) in the PlayerController TakeDamage method. I would have done this by making UIManager inherit from Singleton<UIManager>, then have a method in the UIManager for an enemy dying so the enemy death counter goes up, a method for the player having taken damage that sets the healthbar to the new value, and a method for setting the score to the new score.

Unfortunately I wasn't able to implement a factory in time. Though, I would have used it to spawn bubbles and enemies as previously explained, and I would also have made the generic Factory class inherit from ScriptableObject, and be able to have an Enum where there's only one spawn point, and it could be set as Bubble spawn, or Enemy spawn as I did in my in class activity repo. From the generic Factory class, I would then make EnemySpawn and potentially CoinSpawn, which would contain the logic for spawning and setting the value of coins, or spawning enemies and setting their movement variables. Since the bubbles wouldn't be spawned on Start, the bubbles would instead be called by manually triggering the BubbleSpawn Spawn() method when a certain button is pressed. This would allow only one type of spawn point, so no matter how many things to spawn would be in the game, there would only need to be 1 type of spawn point instead of 20 in the project window. It would also allow different bubble spawn points to be set easily, or be able to add more variables for the enemies that would apply to all enemies (instead of setting prefab variables, potentially in multiple different scripts for different enemy types), and logic for different enemy types could be set easily in one place as well. We could easily have two different types of spawn points, one where the spawn is triggered by a certain button (for bubbles, powerups maybe with a cooldown, etc), and one where the spawn is triggered on Start() (for enemy types).

If I had more time, I would have also had an invisible collider so that if the player falls below the map, they would die instead of having to restart the game. I would also have made a pause menu and restart button when the player dies. Of course, I would have also created pixel art in Krita for the enemies, bubbles, and player, and textured the platforms.
